NiCo – Hilfe

NiCo ist ein lokaler, browserbasierter Konfigurator für NixOS. Er arbeitet direkt mit echten .nix-Dateien auf 127.0.0.1 – ohne Telemetrie, ohne Daten nach außen, ohne eigene Konfig-Welt. NiCo soll Nix nicht ersetzen, sondern die Arbeit damit übersichtlicher und sicherer machen.

1Das Herzstück: Nix-Brix

1.1Was sind Nix-Brix?

Nix-Brix sind frei editierbare Nix-Abschnitte, die NiCo niemals verändert. Wer Konfiguration braucht, die NiCo nicht als Formularfeld kennt – ein Dienst, ein Overlay, eine spezielle Option – schreibt sie als Nix-Brick. NiCo umschließt den Nix-Brick mit Marker-Kommentaren wie # <brick: TAIL / #1 syncthing> … # </brick: syncthing> und lässt den Inhalt dazwischen vollständig unberührt.

Das Konzept ist in dieser Form einzigartig: Statt nur das zu erlauben, was ein GUI-Tool vorgeneriert, bleibt die volle Nix-Freiheit erhalten. Nix-Brix und Formularfelder koexistieren in derselben Datei – NiCo kümmert sich nur um seinen eigenen Bereich.

Daraus ergibt sich der wichtigste Unterschied: Was in einem Formularfeld steht, wird bei jedem Speichern komplett neu erzeugt – was in einem Nix-Brick steht, bleibt unverändert erhalten.

Wichtig: Nix-Brix werden beim Import einer bestehenden Konfiguration automatisch angelegt – unbekannte Abschnitte landen als Nix-Brick 1-imported-config und gehen nicht verloren.

1.2Nix-Brix anlegen und verwalten

Einen neuen Nix-Brick anlegen: Schaltfläche + Nix-Brick einfügen → Bezeichnung eingeben → Einfügen. Der Nix-Brick erscheint am Ende des Dokuments; der Inhalt wird direkt im Codefenster rechts bearbeitet.

Über das Aktionsmenü (⋮) eines Nix-Bricks stehen weitere Funktionen bereit:

  • Umbenennen – ändert die Bezeichnung, die numerische ID bleibt erhalten
  • Verschieben – legt den Nix-Brick in einen anderen Abschnitt oder an eine andere Position
  • Aufteilen – teilt einen Nix-Brick an einer bestimmten Zeile in zwei separate Nix-Brix
  • Löschen – entfernt den Nix-Brick unwiderruflich; der Inhalt geht verloren

Nix-Brix lassen sich auch über die Schaltfläche ⇄ Nix-Brick verschieben in einen anderen Host oder ein anderes Modul übertragen.

1.3Dateitypen

Jede Datei im Config-Verzeichnis wird einem Typ zugewiesen, der bestimmt, welches Panel angezeigt wird:

  • NixOS-Modul – configuration.nix und eingebundene Module; formularbasiert mit Nix-Brix
  • Home Manager – Dateien im HM-Verzeichnis (Standard: home/); eigene Felder pro Benutzer
  • Flake – flake.nix mit Hosts, Channel-Auswahl und Architektur
  • Hardware-Konfiguration – hardware-configuration.nix; schreibgeschützt (NixOS-generiert)
  • Flake Lock – flake.lock; nur Anzeige, keine Bearbeitung über NiCo
  • Nicht erkannte Datei – Textmodus: Direktbearbeitung im Codefenster, Änderungen werden sofort gespeichert

2Erste Schritte

2.1Erster Start

Beim ersten Start fragt NiCo nach dem Config-Verzeichnis. Wer noch keines hat, legt dort ein neues an; wer eine bestehende Konfiguration hat, wählt das vorhandene Verzeichnis.

1. Config-Verzeichnis angeben → NiCo richtet automatisch ein Git-Repository ein und kopiert hardware-configuration.nix aus /etc/nixos (falls vorhanden) 2. Bei gefundener oder fehlender Config: Import-Angebot (siehe 2.2) 3. Optional: Symlink /etc/nixos → Config-Verzeichnis einrichten (damit nixos-rebuild die Konfiguration automatisch findet)

NiCo speichert seine eigenen Einstellungen in ~/.config/nico/settings.json (XDG) – nie im Config-Verzeichnis selbst. Konfigurationseinstellungen wie Verzeichnisnamen für Hosts, Module und Home Manager liegen in {config-dir}/config.json.

2.2Config importieren

Findet NiCo eine bestehende NixOS-Konfiguration im gewählten Verzeichnis, bietet es den Import an. Erkannte Felder werden als Formularwerte übernommen; unbekannte Abschnitte landen als Nix-Brick 1-imported-config und bleiben vollständig erhalten.

  • Nach /etc/nixos sieht NiCo erst, wenn du auf In /etc/nixos nachsehen klickst – nicht von selbst
  • Vor dem Import wird automatisch ein Sicherungspunkt angelegt
  • hardware-configuration.nix wird kopiert, falls vorhanden
  • Import ist auch nachträglich aufrufbar – aus einem anderen Verzeichnis oder einer ZIP-Datei
  • Ist das Zielverzeichnis nicht leer, wird vor dem Import ein Backup angelegt

3Arbeiten mit NiCo

3.1Oberfläche

  • Links – Dateibaum: alle .nix-Dateien im Config-Verzeichnis; Klick öffnet das jeweilige Panel
  • Rechts – Panel: Formularfelder für bekannte Optionen der ausgewählten Datei, darunter die Nix-Brix
  • Admin-Bereich: Einstellungen, Git-Status, Rebuild-Optionen, Sprache und Theme

3.2Vorschau vs. echter Dateistand

Die Schaltfläche Vorschau zeigt, welche .nix-Datei beim nächsten Schreiben erzeugt würde – ohne die Datei auf Platte zu verändern. Dry-Run und Rebuild arbeiten immer mit dem tatsächlichen Dateistand auf Platte, nicht mit dem Formularinhalt.

Merksatz: Formular ändern → Speichern → Dry-Run/Rebuild. Ohne Speichern prüft der Dry-Run den alten Stand.

Achtung: Beim Schreiben wird die gesamte formular-verwaltete Datei neu aufgebaut – NiCo bearbeitet nicht den vorhandenen Text, sondern erzeugt ihn komplett neu. Eigene Kommentare außerhalb von Nix-Brix sammelt NiCo im Nix-Brick imported-notes, jeweils mit dem Ort, an dem sie standen (before networking.hostName, inside services.pipewire …). Ein Kommentar direkt über einem Befehl, der ohnehin ein Nix-Brick wird, wandert mit in diesen Brick. Leerzeilen und manuelle Formatierung außerhalb von Nix-Brix werden entfernt. Unverändert bleibt nur Inhalt innerhalb eines Nix-Bricks.

Wurde eine Datei außerhalb von NiCo geändert – mit einem Editor, über Syncthing oder git pull – oder hat NiCo sie noch nie gespeichert, baut NiCo sie nicht ungefragt um. NiCo erkennt das an der Prüfsumme in der Versionszeile und fragt, bevor das Formular die Datei übernimmt: Umbauen (vorher ein Sicherungspunkt mit dem jetzigen Stand, ohne Git eine ZIP), Unterschiede ansehen (was das Umbauen ändern würde) oder Im Textmodus öffnen (die Datei bleibt, wie sie ist).

3.3Speichern, Dry-Run, Rebuild

1. Speichern → Diskette oder Strg+S schreibt den Stand in die .nix-Dateien auf Platte 2. Dry-Run → prüft, ob Nix die Config bauen kann (nixos-rebuild dry-build) 3. Rebuild → baut das System – Live-Ausgabe im Rebuild-Monitor

Vor jedem Dry-Run und Rebuild läuft der Validator auf dem gespeicherten Stand. Findet er einen kritischen Fehler, zeigt er ihn, statt den Bau zu starten. Mit Git legt NiCo vor dem Rebuild einen Sicherungspunkt (Commit) an; zurück geht es jederzeit über die Zeitmaschine. Sie setzt die Dateien zurück – das laufende System startet weiter aus seiner vorhandenen Generation. Im Flake-Modus fragt NiCo, welcher Host gebaut wird.

Im Dialog Rebuild-Optionen:

  • Modus: switch – jetzt umstellen und künftig so starten (der Normalfall); boot – erst beim nächsten Start; test – nur jetzt, ein Neustart bringt den alten Stand zurück (der sichere Weg zum Ausprobieren)
  • Flake aktualisieren (nix flake update) – nur mit Flakes
  • Abgesicherter Rebuild: begrenzt, wie viele Pakete gleichzeitig (--max-jobs) und mit wie vielen Kernen je Paket (--cores) gebaut werden. Braucht weniger Arbeitsspeicher, dauert aber länger. Leer gelassen, schlägt NiCo Werte aus dem freien Arbeitsspeicher dieses Rechners vor – eine Schätzung, einzelne Pakete brauchen mehr
  • Alle Meldungen von Nix anzeigen: standardmäßig aus. Dann zeigt der Monitor Phasen, Fortschritt, Warnungen und Fehler, aber nicht jede Datei und jeden Store-Pfad, die Nix meldet – darin gingen Warnungen unter. Dieselbe Schaltfläche steht auch im Rebuild-Monitor; dort wirkt sie sofort auf den laufenden Rebuild, schon verworfene Zeilen kommen aber nicht zurück. Ausgeblendete Meldungen fehlen auch in der Logdatei. NiCo merkt sich die Wahl pro Rechner
  • In Terminal-Fenster ausführen sowie Herunterfahren nach dem Rebuild (auf Wunsch nach dem Hochladen der Konfiguration)

Ist im Admin-Bereich die Analyse vor dem Rebuild eingeschaltet, prüft NiCo vorher, was geladen und was kompiliert werden muss. Der Monitor zeigt dann die Download-Größe von Anfang an. Muss ein Paket auf diesem Rechner aus dem Quelltext gebaut werden, fragt NiCo vorher nach und bietet den abgesicherten Rebuild an. Der Start dauert dadurch einige Sekunden länger.

3.4Diesen Rechner lesen

NiCo liest standardmäßig nur das Config-Verzeichnis. Einige Prüfungen müssten auch den Rechner selbst ansehen – das erlaubst du einzeln, unter Einstellungen → NiCo → Diesen Rechner lesen oder mit dem Knopf Freigeben an der Stelle, wo die Funktion es braucht. Nur lesend, nichts verlässt den Rechner; ausschalten geht jederzeit in den Einstellungen.

  • Validator: diesen Rechner prüfen – Benutzer und Gruppen (/etc/passwd, /etc/group), laufende NixOS-Version, Installationsdatum, Swap und Dateisysteme. Ohne Freigabe prüft der Validator alles andere und sagt einmal, welche Prüfungen ausgelassen wurden – darunter die, die vor einem gesperrten Konto warnen
  • Hardware dieses Rechners lesen – /etc/nixos/hardware-configuration.nix und die Datenträger. Ohne Freigabe gibt es keinen Hardware-Abgleich und keine Suche nach Hardware-Dateien; einen Pfad kannst du trotzdem eingeben
  • Systemstände (Generationen) lesen – die Liste der Systemstände für die Zeitmaschine, Seite System

Der Vorschlag beim abgesicherten Rebuild liest den freien Arbeitsspeicher – erst, wenn du den abgesicherten Rebuild wählst; der Dialog sagt es darunter.

4Flakes, Hosts und Home Manager

Flake-Modus

Im Flake-Modus verwaltet NiCo eine flake.nix mit einem oder mehreren Hosts in nixosConfigurations. Das Flake-Panel bietet:

  • Channel-Auswahl: NiCo lädt beim Öffnen die aktuelle nixpkgs-Channelliste (nix-channels.s3.amazonaws.com, rein lesend). Ohne Internetzugang wird eine eingebaute Fallback-Liste verwendet
  • Architektur-Selektor: z. B. x86_64-linux, aarch64-linux
  • Hosts anlegen und löschen über die Oberfläche

Hosts

Jeder Host liegt in einem eigenen Verzeichnis (Standard: hosts/, konfigurierbar). NiCo erkennt alle Hosts aus nixosConfigurations in der flake.nix und stellt sie im Dateibaum dar. Jeder Host hat seine eigene configuration.nix mit eigenen Formularfeldern und Nix-Brix.

Home Manager

NiCo verwaltet Home Manager-Konfigurationen in einem eigenen Verzeichnis (Standard: home/, konfigurierbar). Pro Benutzer gibt es eine eigene .nix-Datei mit eigenen Formularfeldern – darunter home-manager.enable und weitere HM-Optionen. Nix-Brix sind auch in HM-Dateien möglich.

Abschnittsnamen in den Dateien

In den erzeugten Dateien steht jeder Abschnitt unter einem vierstelligen Kürzel: # ── FSYS · Maintenance & snapshots ──, und Nix-Brick-Marker lauten # <brick: FSYS / #2 name>. Pro Flake-Host gibt es HOST:<name>. Das Kürzel ist der Anker, den NiCo liest – der Text dahinter ist für dich und immer englisch, wie die Nix-Optionen ringsum. Übersetzt wird nur die Oberfläche: Panel, Code-Ansicht und Nix-Brick-Dialoge zeigen den Abschnittsnamen in deiner Sprache.

Dateien aus NiCo 0.12.0 und älter tragen deutsche Abschnittsnamen. Die liest NiCo weiterhin und schreibt sie beim nächsten Schreiben auf Kürzel um – ein Nix-Brick behält dabei seinen Abschnitt. Zusätzlich steht in der nico-version-Zeile eine Formatnummer (#f2). Öffnest du eine Config, die mit einer neueren NiCo-Version geschrieben wurde, fragt NiCo nach: Verloren geht nichts, weil unbekannter Inhalt als Nix-Brick erhalten bleibt, aber Blöcke können umsortiert werden – deshalb legt NiCo vorher einen Sicherungspunkt an.

Wartung für alle Dateisysteme

Der Abschnitt „Wartung & Snapshots" beginnt mit Optionen, die unabhängig vom Dateisystem gelten – sie sind also auch bei ext4, xfs oder f2fs sinnvoll:

  • Festplatten-Überwachung: services.smartd.enable – der SMART-Daemon liest die Selbstdiagnose der Laufwerke und meldet Fehler, bevor eine Platte ausfällt
  • /tmp im Arbeitsspeicher: boot.tmp.useTmpfs – /tmp liegt im RAM, ist nach jedem Start leer und schont die SSD. Die Größe (boot.tmp.tmpfsSize, Standard 50%) nimmt Prozent oder Bytes; große Nix-Builds brauchen dort Platz.
  • /tmp beim Booten leeren: boot.tmp.cleanOnBoot – für ein /tmp auf Platte. Bei /tmp im Arbeitsspeicher ist der Schalter ausgegraut, weil ein tmpfs beim Start ohnehin leer ist; der gespeicherte Wert bleibt erhalten.

Für ext4 gibt es darüber hinaus keine Wartungsjobs: Snapshots kennt das Dateisystem nicht, und einen Scrub-Dienst gibt es in NixOS dafür nicht. Nutzt dieser Rechner kein btrfs, weist NiCo über der Btrfs-Gruppe darauf hin.

Btrfs (Auto-Scrub und Auto-Balance)

NiCo kann systemd-Timer und -Services für regelmäßige Btrfs-Wartung generieren:

  • Auto-Scrub: prüft regelmäßig die Integrität des Btrfs-Dateisystems
  • Auto-Balance: gleicht die Datenverteilung aus; konfigurierbar mit Häufigkeit, dusage- und musage-Schwellwerten

5Git-Integration

5.1Sicherungspunkte und Zeitmaschine

Ist das Config-Verzeichnis ein Git-Repository, legt NiCo Sicherungspunkte (Commits) an: nach jedem Speichern, vor jedem Rebuild, vor einem Import und bevor eine Datei überschrieben oder umgebaut wird. Nach einem erfolgreichen Rebuild bietet der Monitor Sicherungspunkt anlegen (Commit) bzw. Sicherungspunkt anlegen & hochladen (Commit & Push) an. Ohne Git sichert NiCo vor solchen Schritten als ZIP-Datei.

Die Zeitmaschine (Admin-Bereich, Tab „Zeitmaschine“) listet die Sicherungspunkte. Wiederherstellen (Restore) holt die Nix-Dateien eines beliebigen davon zurück – als neuer Commit, die Historie bleibt vollständig erhalten. Die Zeitmaschine hat dafür die Seite Config.

Wiederherstellen betrifft die Dateien, nicht das laufende System. Das startet weiter aus seiner aktuellen Generation, bis du neu baust – oder im Bootmenü eine ältere Generation wählst.

5.2Startwächter und Änderungen von außen

Beim Start vergleicht NiCo den lokalen Stand mit dem Remote, bevor es eine Datei lädt. Ist alles gleich, merkst du davon nichts. Sonst erscheint ein Dialog mit dem letzten Stand auf beiden Seiten und den Sicherungspunkten, die einer Seite fehlen – mit Datum, Autor und Beschriftung, sodass du siehst, auf welchem Rechner zuletzt geändert wurde:

  • Remote ist weiter (z. B. auf dem Laptop gearbeitet und hochgeladen): Alles vom Remote holen ersetzt den lokalen Stand
  • Beide Seiten haben eigene Sicherungspunkte: holen oder den lokalen Stand erzwungen hochladen – eine Seite verliert dabei ihre Änderungen, der Dialog sagt welche
  • Ungesicherte lokale Änderungen: verwerfen (lokale Sicherungspunkte bleiben) oder hochladen
  • Abbrechen öffnet NiCo ohne Config – nichts wird angefasst

Ändert sich eine Datei außerhalb von NiCo – Editor, Syncthing, git pull –, übernimmt NiCo sie nicht stillschweigend. Beim Öffnen fragt es: Umbauen (der Stand davor kommt vorher in einen Sicherungspunkt bzw. eine ZIP-Datei), Unterschiede ansehen oder Im Textmodus öffnen, der die Datei lässt, wie sie ist. Ändert sie sich, während das Formular offen ist, fragt NiCo vor dem Speichern: Neu laden, Unterschiede ansehen oder Überschreiben.

5.3Remote-Repository und Hochladen

Die Remote-URL (z. B. ein GitHub-Repository) wird im Admin-Bereich eingerichtet. Unter „Git-Synchronisation“ lässt sich einstellen, ob NiCo nach dem Speichern bzw. nach einem erfolgreichen Rebuild automatisch hochlädt; ohne diese Einstellung bietet der Monitor nach dem Rebuild Sicherungspunkt anlegen & hochladen an. Ist beim Schließen noch etwas nicht hochgeladen, weist NiCo darauf hin.

Ein Rechner ohne Remote arbeitet nur lokal: Sicherungspunkte und Zeitmaschine funktionieren genauso, nur das Hochladen entfällt.

5.4Fremddateien und Git-Hygiene

Liegen im Config-Verzeichnis Dateien, die nicht zur NixOS-Konfiguration gehören (z. B. Scripts, README, Sicherungen), fragt NiCo vor dem Sicherungspunkt pro Datei, ob sie in Git aufgenommen oder ausgenommen (auf die .gitignore gesetzt) werden soll. Die Abfrage lässt sich in den Admin-Einstellungen abschalten.

Für bereits in Git erfasste Fremddateien gibt es im Admin-Bereich einen Aufräum-Dialog: Austragen entfernt die Datei aus Git und setzt sie auf die .gitignore (die Datei bleibt auf der Platte, die Historie bleibt erhalten); Behalten merkt sich die Datei dauerhaft als gewollt.

Eine zu große Datei nimmt NiCo nicht in einen Sicherungspunkt auf und sagt es – sonst blockierte sie irgendwann jedes Hochladen. Beim Start meldet der Dialog Git-Hygiene, was schon in die Versionierung geraten ist (fehlende .gitignore-Einträge, alte Rebuild-Protokolle, Fremddateien, zu große Dateien), und bietet Jetzt beheben an.

6Import, Export und Entkoppeln

Diese Funktionen sind über den Admin-Bereich erreichbar.

Import

Eine bestehende NixOS-Konfiguration aus einem Verzeichnis oder einer ZIP-Datei einlesen. Erkannte Felder werden übernommen, unbekannte Abschnitte als Nix-Brick gesichert. Ist das Zielverzeichnis nicht leer, wird vor dem Import ein Backup angelegt.

Export

Die gesamte Konfiguration als ZIP-Datei herunterladen – alle .nix-Dateien aus dem Config-Verzeichnis werden eingepackt. Nützlich als Backup oder zum Übertragen auf ein anderes System.

Entkoppeln

NiCo löst die Verbindung zum Config-Verzeichnis. Vorher wird automatisch ein ZIP-Backup angelegt. Dann entfernt NiCo seine Marker-Kommentare aus den .nix-Dateien (der Nix-Inhalt bleibt vollständig erhalten) und löscht config.json bzw. eine alte nico.json. Das Verzeichnis ist danach eine reine Nix-Konfiguration ohne NiCo-Spuren und kann manuell oder mit einem anderen Tool weiterverwendet werden.

7Typische Fehler und Grenzen

Dry-Run oder Rebuild schlägt sofort fehl

Wahrscheinlichste Ursache: Formularinhalt wurde noch nicht gespeichert. Dry-Run und Rebuild arbeiten immer mit dem Stand auf Platte – zuerst Speichern (Diskette oder Strg+S), dann prüfen oder bauen.

Nix-Fehler im Dry-Run/Rebuild

Die vollständige Ausgabe von Dry-Run und Rebuild ist direkt im Stream sichtbar. Nix-Fehlermeldungen können dort gelesen werden. Häufige Ursachen sind Syntaxfehler in Nix-Brix oder Referenzen auf nicht existierende Pakete.

Scheitert der Bau an einem einzelnen Paket, lässt es sich in der Paketliste deaktivieren statt löschen: Der Schalter neben dem Paket nimmt es aus dem Bau, der Eintrag bleibt ausgegraut stehen und muss später nicht neu gesucht werden. In der Datei liegen deaktivierte Pakete im Nix-Brick nico-inactive-packages, den NiCo selbst verwaltet.

Bricht ein AppImage mit cannot open shared object file ab, fehlt ihm eine Bibliothek. Ihr Paketname gehört in das Feld „Zusätzliche Bibliotheken“ unter dem AppImage-Support (Abschnitt Programme) – der Paketname, nicht der Dateiname: libgpg-error, nicht libgpg-error.so.0.

NiCo erkennt eine .nix-Konstruktion nicht

Komplexe oder ungewöhnliche Nix-Syntax, die NiCo nicht parsen kann, wird niemals gelöscht. Solche Abschnitte bleiben als Nix-Brick erhalten. Bei einem Import landen sie automatisch im Nix-Brick 1-imported-config.

hardware-configuration.nix kann nicht bearbeitet werden

Diese Datei ist in NiCo schreibgeschützt, weil sie von NixOS automatisch generiert wird. Manuelle Änderungen daran sind zwar technisch möglich, können aber beim nächsten nixos-generate-config überschrieben werden.

Snapper-Validator meldet Fehler

Der Validator prüft, ob konfigurierte Snapper-Mountpoints existieren und tatsächlich btrfs-Dateisysteme sind. Ist ein Mountpoint nicht gemountet oder kein btrfs, wird das als Fehler gemeldet. Das ist kein NiCo-Fehler, sondern ein Hinweis auf eine inkonsistente Systemkonfiguration.

Validator-Meldung: Btrfs-Wartung ohne btrfs

Auto-Scrub oder Auto-Balance sind eingeschaltet, obwohl auf diesem Rechner kein btrfs eingebunden ist. Die Config baut und bootet, die Jobs laufen aber ins Leere. Der Auto-Balance-Job arbeitet zusätzlich fest auf / – liegt das btrfs woanders, meldet der Validator das getrennt. Geprüft wird der laufende Rechner, nicht die Config: Bei mehreren Flake-Hosts gilt das Ergebnis nur für den Host, auf dem NiCo läuft.

Validator-Meldung: host_orphaned

Ein Host-Verzeichnis existiert, ist aber nicht in nixosConfigurations der flake.nix eingebunden. Das kann Absicht sein (z. B. ein Host im Aufbau). NiCo meldet es als Hinweis, nicht als Fehler.

Grenzen von NiCo

  • NiCo ist kein Paket-Browser und keine Suchmaschine für Nix-Optionen
  • NiCo generiert keine Konfiguration aus dem Nichts – es arbeitet immer mit bestehenden oder manuell erstellten .nix-Dateien
  • NiCo ist kein Ersatz für das Lesen der NixOS-Dokumentation oder des NixOS-Wikis
  • NiCo läuft nicht auf mehreren Rechnern gleichzeitig – es ist ein lokales Werkzeug für eine Maschine
  • NiCo erhält keine eigene Formatierung außerhalb von Nix-Brix – formular-verwaltete Dateien werden bei jedem Schreiben komplett neu erzeugt; eigene Kommentare landen im Nix-Brick imported-notes, nur Inhalt in Nix-Brix bleibt wörtlich erhalten
